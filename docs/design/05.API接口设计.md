# 云河FC API 接口设计

- 文档版本：v0.9（枚举 code+label 与第二轮评审修正）
- 编写日期：2026-11-09
- 依据：需求 v1.15、`docs/design/01~04`、`docs/rules/api-rules.md`、`kafka-rules.md`、`logging-rules.md`、`prototype/`
- 范围：接口路径、方法、参数、响应、权限、错误与幂等；不写代码、不实现接口、不修改表结构

## 1. 说明

- C 端接口在 `/api/v1/c/**`，B 端在 `/api/v1/b/**`；路径前缀同时决定会话命名空间（`YHFC_C` / `YHFC_B`）。
- 响应字段使用 camelCase，与数据库 snake_case 字段一一对应；计算字段（如 `confirmedCount`）由查询派生，不新增数据库字段。
- 数据库枚举存 TINYINT 数字；API 响应同时返回数字 code 与 `<field>Label` 大写字符串（如 `status=0`、`statusLabel="SIGNUP_OPEN"`），请求只接受数字 code，Label 只读；映射见 04 §2.4。
- 时间使用 ISO-8601 UTC，例如 `2026-11-12T12:00:00.000Z`。
- 本文的接口 ID（如 `AUTH-10`、`MAT-02`）与需求文档的需求 ID（如 `AUTH-01`、`MATCH-01`）是两套独立编号，前缀相同不代表同一编号；`PLAYER-*` 需求对应本文 `PLR-*` 接口。
- 分享链接（需求 MATCH-13、NOTIFY-02）由前端基于 `/matches/{id}` 生成并复制，不新增分享接口。

## 2. 通用约定

### 2.1 统一响应

成功与失败使用同一 envelope，`code` 为数字：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "requestId": "req-7f3c..."
}
```

失败示例：

```json
{
  "code": 40001,
  "message": "参数校验失败",
  "data": {
    "details": [
      { "field": "jersey", "message": "号码已被占用" }
    ]
  },
  "requestId": "req-7f3c..."
}
```

- `code=0` 成功；其余为业务错误码。下文用错误名称指代对应数字码，响应返回数字。
- HTTP 状态码表达类别：200/201、400、401、403、404、409、422、429、500；HTTP 状态在响应行表达，body 只含 `code/message/data/requestId`，两者必须一致。
- `requestId` 由服务端生成并回写响应头 `X-Request-Id`。

### 2.2 分页

请求：`page`（默认 1，≥1）、`pageSize`（默认 10，可选 20/50/100）。
响应 `data`：

不分页例外：角色列表（ROL-01）、权限目录（ROL-06）、阵型模板（LIN-05）、事件时间线（EVT-01）、球队统计（STA-01）返回 `{items}`（EVT-01 另含 `derivedScore`，STA-01 另含 `season`）；PLR-01 使用 `limit/all` 的位置分组预览例外。其余列表统一使用下述 `Page` 结构。

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "pageSize": 10,
  "totalPages": 0
}
```

### 2.4 认证、会话与 CSRF

- C/B 端分别使用 `YHFC_C`、`YHFC_B` 会话 Cookie；`HttpOnly`、`SameSite=Lax`，生产 `Secure`。
- 登录前调用 `GET /api/v1/{c|b}/auth/csrf`，token 在响应体，不使用 CSRF Cookie；写请求携带 `X-XSRF-TOKEN`。
- 登录成功后轮换 Session ID 与 CSRF token；登出/过期后重新获取。
- 微信授权回调走 C 端路径，使用 OAuth `state` 关联会话；`redirect` 只允许站内白名单路径。
- 待审核（PENDING）允许公开读、C 端登录/登出（AUTH-04/05）、AUTH-01/14、AUTH-10、AUTH-02/03/06/07/08/09、INV-01/02、PLR-03、FIL-01、NTF-01~04（只读与标记已读）；其他写接口返回 `ACCOUNT_PENDING`（40303）。账号状态判断优先于角色权限；PENDING 创建时分配 GUEST 角色（P-03 已确认）。B 端登录仍需后台权限，PENDING 不具备。
- 注销（DISABLED）不可登录，不可通过邀请、微信或手机号找回重新激活。

### 2.5 权限

- 权限码格式统一为三段式 `资源:动作:范围`；需求文档中的 `role:manage` 等为简写，落地时补全为 `role:manage:any`。服务端按权限码校验，B 端额外校验后台分区权限。
- 新增邀请权限点：`invite:manage:any`（管理员管理邀请）、`invite:create:match`（正式球员创建比赛邀请）。`match` 是对象范围例外，表示仅允许创建比赛邀请，不扩展通用 scope 枚举。
- 无权限访问返回 403；未登录返回 401；不要用 404 隐藏权限。

### 2.6 幂等与乐观锁

- 高风险写接口要求 `Idempotency-Key: <uuid>`：报名/取消/移除、考勤标记与补录、事件创建/修改/删除、比分、比赛创建/状态/延期/取消/重新排期、邀请创建/撤销、审核/转正/注销、阵容保存、分组生成/调整/保存/清除、设置修改、角色权限与用户角色分配。以各接口表的标注为准。
- 同一用户 + 接口 + 幂等键 + 相同请求哈希：返回首次结果；请求哈希不同返回 `IDEMPOTENCY_KEY_REUSED`。
- 阵容、比赛状态、事件修改请求体携带 `version`；不匹配返回 `VERSION_CONFLICT`。

### 2.7 限流、上传与文件

- 短信、登录、报名等关键接口按账号/IP 限流；超限 429，附 `Retry-After`。
- 头像上传 `multipart/form-data`，服务端校验类型与大小（≤2MB），写入私有 OSS；响应返回业务 `url` 与短期 `signedUrl`。

### 2.8 枚举 code 与 label

- 数据库枚举存 TINYINT 数字；响应中每个枚举字段同时返回数字 `field` 与字符串 `fieldLabel`，例如 `status:0,statusLabel:"SIGNUP_OPEN"`。
- 请求体只接受数字 code；`*Label` 为只读派生字段，服务端忽略客户端传入的 Label。
- 字段映射见 04 §2.4；布尔字段（如 `active`、`manualStatus`、`includeGuests`）不生成 Label。
- 数组枚举字段返回 code 数组与对应 `*Labels` 数组，例如 `secondaryPositions` 与 `secondaryPositionLabels`。
- 下文业务规则中使用的大写枚举名（如 `SIGNUP_OPEN`、`CONFIRMED`）仅表示 `*Label` 语义，实际请求值使用对应数字 code。

## 6. 已确认的接口取舍

- `invite:manage:any` 加入权限种子；正式球员只使用 `invite:create:match`。
- 分组生成即持久化草稿，调整后 save 写快照。
- 首页不提供聚合接口，由前端组合赛程/个人接口。
- 管理员换绑手机号/解绑微信使用 `player:edit:any`。
- 头像上传返回 URL，保存资料时写入 `player.avatar_url`。

P-01~P-15 已确认，见 `docs/design/06.设计方案评审结果.md` §8；接口层无阻塞项。
