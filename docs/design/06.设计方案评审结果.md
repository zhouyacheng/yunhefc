# 云河FC 设计方案评审结果

- 文档版本：v1.33（M02 01：球员管理端读模型与 PlayerAdmin 契约）
- 评审日期：2026-11-09
- 评审范围：需求 v1.15、`docs/design/01`–`05`、`docs/rules/*`、`scripts/sql/schema.sql`、`scripts/sql/quartz.sql`、`prototype/`
- 评审结论：**通过**。可明确判断的文档/SQL 问题已修正；P-01~P-25 已逐一确认并回写 01–06。
- 本轮约束：需求文档已升级 v1.15；不写后端业务代码、不实现 API、不执行 SQL、不更换技术栈；`prototype/` 已按设计修复并回归。

## 1. 评审方法

- 逐份通读需求、01–05、五份规则、业务 DDL 与原型脚本。
- 用 `codebase-design` 的深模块/依赖方向视角检查模块边界；用 `domain-modeling` 的统一语言视角检查术语与状态命名。
- 用子代理分别做需求覆盖矩阵、DB/API 字段核对、原型对照与计划校验，再人工合并、去重、复核。
- 静态检查：表数量、物理外键、Markdown 表格列数、版本引用、权限码与文档交叉引用。
- 评审阶段未执行生产 SQL；V5 后在本地 Docker MySQL 做过迁移验证（见 §30）；原型已按设计修复并回归；需求文档已升级 v1.15。

## 4. 架构合理性检查

| 编号 | 结论 |
|---|---|
| A-01 | 模块化单体、单部署单元、C/B 双 SPA、MySQL 事实源、Outbox/Kafka、Quartz 的总体形态合理，符合单队规模 |
| A-02 | `query`/`stats` 作为只读读模型是合理的深模块；但原 03 §6.2“仅 grouping 可依赖 stats”与 `Query --> Stats` 图冲突，已改为“query 与 grouping 可经 stats 只读接口依赖” |
| A-03 | 原 `Lineup --> Grouping` 直接耦合偏紧，已改为经 Registration/Grouping 的 roster read port，避免业务域依赖 `query` |
| A-04 | 权限判断统一经 `common` 的 PermissionChecker；账号状态/身份读取经 auth 只读 port；业务域不直接依赖 auth 领域实现，Player 不反向依赖 Auth |
| A-05 | 账号审核/转正/注销同时改 User、Player、UserRole、Registration（报名取消与递补）；P-05 已确认新增第三个显式事务例外，仅限这三个用例 |
| A-06 | Quartz 任务补齐审计年度导出；缺勤判定使用 `status_updated_at` 作为提前结束的实际结束时间；场次编号在球队行锁内分配 |
| A-07 | 统计汇总表只存出场/进球/助攻；出场率分母由比赛 read port 提供，P-09 已确认按“本赛季已结束且未取消的球队比赛数” |

### 5.2 状态/时间边界

- 签到由窗口驱动：已确认报名 + 未取消/延期 + 开赛前 4 小时至当天 23:59（Asia/Shanghai 推导后转 UTC）。02 §8.1 已修正为报名中/截止/锁定/进行中/已结束均可在窗口内签到。
- 阵容在非终态且未延期时可编辑，终态与 POSTPONED 禁用；02 §8.1 已与 LIN-03 对齐。
- 已结束比赛可补录/24h 内修改事件、可修正比分；02 §5.3 已修正“赛况只读”的表述。
- 延期（MAT-07）置为 POSTPONED；重新排期（MAT-11）后回 SIGNUP_OPEN；Quartz 自动流转跳过 POSTPONED（P-02 已确认）。
