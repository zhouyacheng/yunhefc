# API 接口设计规范

## 1. 目的与基本原则
本规范用于统一 HTTP API 的设计、实现和维护，确保接口一致、易理解、安全且便于测试。默认以 REST 风格 HTTP API 为参考；如采用其他风格，应在项目设计文档中说明。



## 2. 路径与 HTTP 方法
1. 路径应清晰、稳定，默认使用小写英文和项目统一的命名风格。
2. 资源路径通常使用名词表达，例如 `/matches`、`/matches/{matchId}/registrations`，避免含糊名称和无必要的动词。
3. HTTP 方法应表达明确语义：
   - `GET`：读取资源，不应产生业务副作用。
   - `POST`：创建资源或执行非幂等操作。
   - `PUT`：整体替换资源，需明确语义。
   - `PATCH`：部分更新资源。
   - `DELETE`：删除资源。
4. 路径参数用于标识资源；查询参数用于筛选、排序和分页；请求体用于提交创建或更新数据。
5. 不得将密码、令牌等敏感信息放入 URL 查询参数。
6. 统一使用 `/api/v1` 前缀；破坏性变更通过新版本，不直接改变现有语义
7. C 端接口使用 `/api/v1/c/**`，B 端接口使用 `/api/v1/b/**`；两端会话独立，权限统一由 RBAC 判定，B 端额外校验后台分区权限



## 3. 请求参数与校验
1. 每个接口应明确参数名称、类型、是否必填、默认值、格式和校验规则。

2. 服务端必须校验所有客户端输入，不能只依赖前端校验。

3. 对字符串长度、数值范围、枚举值、日期格式和数组大小设置合理限制。

4. 报名、录事件、保存阵容等写接口支持 `Idempotency-Key` 请求头；同一键重复提交应返回同一结果，不产生重复数据。

5. 需要认证的写请求携带会话 Cookie，并通过 `X-XSRF-TOKEN` 提交 CSRF token；token 从登录或 `auth/csrf` 响应体获取，不使用 CSRF Cookie。

6. 文件上传使用 `multipart/form-data`；后端校验类型与大小（头像上限 2MB）后写入私有 OSS，业务表只存 URL，展示时使用短期签名 URL。

   

## 4. 统一响应格式
1. 项目必须统一成功和失败响应结构，并在 API 设计文档中确认最终格式。
2. 同类接口应使用一致的字段命名和数据类型。
3. 响应只应包含调用方需要的数据，不应默认暴露数据库内部字段或敏感信息。
4. 列表接口应统一分页结构；默认 10 条，可选 20/50/100；页码起始值在接口设计阶段确认。
5. HTTP 状态码与业务成功标记不得互相矛盾；不得将所有错误都返回为 HTTP 200。



## 5. HTTP 状态码与业务错误码
1. 使用合适的 HTTP 状态码表达成功、创建成功、参数错误、未认证、无权限、资源不存在、冲突、请求过多（限流）和服务端错误等结果。
2. 业务错误码应稳定、可识别，并统一命名或编号规则；错误响应统一包含错误码、HTTP 状态与 `requestId`。
3. 错误响应应提供足够的处理信息，但不得泄露内部实现细节。
4. 参数校验错误应尽可能指出相关字段及原因。
5. 不应仅凭 HTTP 200 判断业务操作成功。
