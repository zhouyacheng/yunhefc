# 数据库设计规范

## 1. 目的与基本原则
本规范用于指导数据库概念、逻辑和物理设计，保证数据模型一致、完整、安全且易维护。



## 2. 命名规范
1. 数据库对象默认使用小写英文和下划线分隔的 `snake_case`。
2. 表名、字段名应表达明确业务含义，避免拼音、无意义缩写和含糊名称。
3. 表名单复数风格应在项目中统一。
4. 主键默认命名为 `id`；逻辑关联字段采用关联实体名加 `_id`，例如 `user_id`。
5. 时间字段应明确表达含义，例如 `created_at`、`updated_at`。
6. 避免使用数据库保留字作为对象名称。
7. 命名规则一经确认，应在新增表和字段中保持一致。



## 3. 表与字段设计
1. 字段类型应准确表达数据含义，避免所有字段统一使用字符串或过大的类型。

2. 必填字段应设置 `NOT NULL`；仅在业务允许缺失时使用可空字段。

3. 默认值必须有明确业务含义，不得掩盖数据缺失或无效状态。

4. 金额等需要精确计算的数据应使用适合的定点数类型，避免浮点数误差。

5. 日期时间字段统一使用 UTC 存储，接口返回 UTC，展示层按 Asia/Shanghai 转换。

6. 状态字段应具有明确、有限且有文档说明的取值集合。

7. 不得将多个独立业务值拼接到一个字段，除非该字段确实表示不可拆分内容或采用明确约定的结构化存储。

   

## 4. 主键、外键与完整性约束
1. 表必须设计主键，主键必须唯一、非空，并稳定标识一条记录；主键生成策略在数据库设计阶段确认后统一执行。
2. 表之间通过逻辑关联字段建立关系，由应用层负责关联校验和业务完整性维护；本项目业务表不创建物理外键，Quartz 官方表自带的外键为框架例外。
3. 业务上必须唯一的值应使用唯一约束，而不应只依赖应用代码检查。
4. 数据完整性不能只依赖前端校验；服务端应校验输入，数据库约束应作为重要防线。

## 5. 索引

1. 高频查询、分页排序和逻辑关联字段应建立索引；索引以实际查询与执行计划为依据，避免无查询支撑的冗余索引。
2. 列表分页查询优先使用覆盖索引，减少回表。
3. 唯一约束由数据库唯一索引实现，不依赖应用层判重。
4. 索引变更通过 Flyway 迁移脚本管理，不在生产环境手工执行 DDL。

## 6. 迁移变更

1. 数据库迁移统一使用 Flyway，随应用启动执行；禁止手工改表或在生产环境直接执行 DDL。
2. 迁移脚本保持小步、向后兼容；长迁移拆分为多次发布。
3. 采用 expand/contract：先新增兼容字段，再切换读写，最后清理旧字段；切换期间保持新旧字段兼容读写。
4. 回滚优先仅回滚代码；仅当迁移不向后兼容时，按备份/PITR 恢复，不做逆向迁移。
5. 启动健康检查覆盖迁移结果；迁移失败应阻断启动。
